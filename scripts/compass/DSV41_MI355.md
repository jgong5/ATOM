# DeepSeek-V4.1-Flash, DP attention + EP, on one MI355X node: one real run, fit, simulate, compare

Two cells, each from **one** real GPU run, the law fitted on that run's own record
and the simulated run compared against it (an in-sample check: one run carries no
spread, so `python -m atom.compass.validate`, which needs two `real*/` runs, is
replaced by `scripts/compass/one_real.py`):

| Cell | Layout on one 8-GPU MI355X node | Client |
|---|---|---|
| A, aggregated | one server, `-tp 4 --enable-dp-attention --enable-expert-parallel` (DPA4-EP4) on GPUs 0-3 | c=128 |
| B, 1P1D | P: DPA4-EP4 on GPUs 0-3; D: DPA4-EP4 on GPUs 4-7; Mooncake P/D; atomesh | c=128 |

The flags follow `recipes/DeepSeek-V4.1-6P16D-C1228-Share-Cache.md` (ROCm/ATOM
`lirzhang/recipe-6p16d-c1228-share-cache-20261117`): P's settings for the
aggregated server and the prefill side, D's for the decode side, without the
Mooncake Store (no `multi` connector, no offload; so no `share_cache` routing,
which needs a tier every rank shares: every side keeps ATOM's default
`least_requests`, the recipe's decode policy). Change `W` for DPA2 / DPA8.

  digest changes.
- A GPU container with `--device /dev/kfd --device /dev/dri`, for cell B also
  `--device /dev/infiniband`, and `--cap-add IPC_LOCK --ulimit memlock=-1 --network host
  --ipc host`, the model at `/models/dsv41`, cc-traces at `/cc`, and a data directory.
  Simulated runs need no GPU (`on_arch` declares gfx950 on a host without `/dev/kfd`).
- `git config --global --add safe.directory '*'`; the tree is a clean checkout of this
  branch (`T`): fits and the router LP refuse a dirty tree.
- **Host memory: the Engram tables.** Under DP attention each rank's attention runs at
  TP 1 and reads the whole 183.1 GiB table. Upstream's default for that case
  (`ATOM_ENGRAM_UVA=1`, `ATOM_ENGRAM_UVA_COPY` unset) registers the checkpoint's shared
  read-only mapping in place: the page cache is pinned once a node, about 196 GB,
  whatever the ranks, so cell A and cell B (both servers map the same checkpoint
  files) each pin about 196 GB, not 183 GiB a rank. #3425's 183 GiB a rank were copies,
  at an older tree. It needs, on the host (root), `sysctl -w vm.compact_unevictable_allowed=0
  vm.compaction_proactiveness=0` (else kcompactd migrates the registered pages and
  each migration evicts the GPU queues: decode stalls or a hang); every rank sharing
  `/dev/shm` for the registration lock (`--ipc host`, or `ATOM_ENGRAM_REG_LOCK` on a
  path all see); and `memlock` unlimited or `CAP_IPC_LOCK`. Each rank logs `engram: UVA
  device lookup active ... page-locked`, or `engram: using the host path` where it fell
  back; `numactl -H` before and after shows the pin. The fallbacks, `ATOM_ENGRAM_UVA_COPY=1` (a copy a rank: about 730 GiB for cell A,
  1.46 TiB for cell B), `ATOM_ENGRAM_UVA_HBM=1` (the table in HBM: no KV left beside
  the weights) and `ATOM_ENGRAM_UVA=0` (a host gather, about 50 ms of CPU a decode step,
  MI455 A0's bring-up), change the step times: record, fit and simulate under one
  setting. See `docs/environment_variables.md`, `ATOM_ENGRAM_UVA*`.
- The router: build atomesh from this tree, with the image's lockfile (Cargo.lock is
  ignored, so the checkout stays clean):

## Cell A: aggregated, DPA4-EP4, c=128

```bash
G=0,1,2,3; A=$R/a; mkdir -p $A/logs
compass measure memory --gpu $G --out $A/memory $S -- $(args agg)
# the one real run: a record, its client at 128 for D seconds, stopped by the client
compass record --gpu $G --out $A/real1 $S -- $(args agg) > $A/logs/real1.log 2>&1 &
until [ -s $A/real1/server.json ]; do sleep 10; done
HARNESS_PYTHON=$REAL_PY $T/scripts/compass/client.sh $A/real1 --agentx --concurrency 128 --duration 1800 --stop
wait
# the fits: the prefill vector labelled from the record's own device window
# (0c86ce343), and only the graded window's steps, its warmup left out (db0b89a32:
# on MI455's DEP4 record a law fitted on every step put TPOT p50 at +11.3%, on the
# window +1.3%, the Engram page cache filling over the warmup)
COMPASS_PREFILL_LABEL=record COMPASS_FIT_GRADED_ONLY=1 compass fit steps --backend step-linear --form history --model $MODEL \
  $A/real1 --client-run $A/real1 $A/real1/artifacts/client_run.json $S --out $A/fit/steps | tee $A/logs/fit_steps.log

token() { awk '/^published / {t = $NF} END {print t}' "$1"; }
LAW=$(token $A/logs/fit_steps.log) HOST=$(token $A/logs/fit_host.log)

compass run --step-linear $LAW --host-laws $HOST $P $S --out $A/step_linear -- $(args agg) > $A/logs/sim.log 2>&1 &

HARNESS_PYTHON=$SIM_PY $T/scripts/compass/client.sh $A/step_linear --agentx --concurrency 128 --duration 1800 --stop

PYTHONPATH=$T python3 $T/scripts/compass/one_real.py $A/real1 $A/step_linear
```

`one_real.py` prints TTFT p50 / p99, TPOT p50 / p90, E2E p50, throughput per GPU and
the InferenceX metrics of each run, with the simulated run's relative error. Check the
law first: `$A/fit/steps/step_linear_law.json` should read `"unfitted": {}`, and the
decode rungs the c=128 run reached (32 a rank) should each hold a vector; a missing
rung refuses every step at it.

## Cell B: 1P1D on one node, DPA4-EP4 a side, c=128

KV moves through Mooncake. On a node whose GPUs each have an RDMA HCA, leave
`protocol` at rdma. On a node with none, set `KV_EXTRA='{"protocol":"tcp"}'`: slow, and
README.md notes TCP transfers that time out at high concurrency. Under
`--kv-over-network` the simulated KV is priced on `--network`'s link:
`nic-400g` (assumed: 50 GB/s, 5 us, derate 0.8) until a measured one replaces it.
`ATOM_MOONCAKE_MATCHED_RAILS=auto` pairs rail N with rail N on another node; with
both sides on one node, P's GPU N writes to D's GPU N+4, so leave it unset unless
the fabric routes those rails to each other. Where the hosts load no peer-memory
module for the HCAs, `ibv_reg_mr` on GPU memory fails unless
`MOONCAKE_DISABLE_HIP_DMABUF=0` (the image and the recipe set `1`), and amdgpu then
counts each registered buffer twice: README.md saw DeepSeek-V4-Pro run out of
memory at `--gpu-memory-utilization 0.85` right after registration. If the
prefill side does, lower its `HBM` to 0.75 in `args` for every step (readings,
record, fit and run alike).

```bash
B=$R/b; mkdir -p $B/logs
ROUTER="--backend atom --model-path $MODEL --policy cache_aware --prefill-policy cache_aware \
  --decode-policy cache_aware --cache-threshold 1.0 --balance-abs-threshold 0 --balance-rel-threshold 1.0 \
  --disable-circuit-breaker --request-timeout-secs 1800"
for side in P D; do  # memory readings per side, each on its own cards, under Mooncake
  g=$([ $side = P ] && echo 0,1,2,3 || echo 4,5,6,7)
  role=$([ $side = P ] && echo kv_producer || echo kv_consumer)
  # KV_EXTRA's fields too, so the start registers its memory as the record's does
  kv=$(python3 -c 'import json, os, sys
print(json.dumps({**json.loads(os.environ.get("KV_EXTRA") or "{}"), "kv_role": sys.argv[1], "kv_connector": "mooncake"}))' $role)
  compass measure memory --gpu $g --out $B/memory-$side $S -- $(args $side) --kv-transfer-config "$kv"
done
# the one real run
ATOMESH=$ATOMESH $T/scripts/compass/deploy.sh $B/real1 record --kv-over-network $S \
  --prefill --gpu 0,1,2,3 -- $(args P) --decode --gpu 4,5,6,7 -- $(args D) \
  --router -- $ROUTER > $B/logs/real1.log 2>&1 &
until [ -s $B/real1/server.json ]; do sleep 10; done
HARNESS_PYTHON=$REAL_PY $T/scripts/compass/client.sh $B/real1 --agentx --concurrency 128 --duration 1800 --stop
wait
for side in prefill decode; do  # a law and host laws per side
  COMPASS_PREFILL_LABEL=record COMPASS_FIT_GRADED_ONLY=1 compass fit steps --backend step-linear --form history --model $MODEL \
    $B/real1/$side --client-run $B/real1/$side $B/real1/artifacts/client_run.json $S \
    --out $B/fit/$side-steps | tee $B/logs/fit_$side-steps.log
  # the prefill side's entry also states the hops no record times (093d1d9c5):
  # the router's forward, #3009's assumed 1.5 ms, and Mooncake's write request,
  # #2603's 0.106 ms; a --dp-aware router LP refuses without router_s
  stated=(); [ $side = prefill ] && stated=(--stated-hop router_s=0.0015 --stated-hop kv_write_req_s=0.000106)
  COMPASS_FIT_GRADED_ONLY=1 compass fit host $B/real1/$side --client-run $B/real1/$side $B/real1/artifacts/client_run.json $S \
    "${stated[@]}" --out $B/fit/$side-host | tee $B/logs/fit_$side-host.log
done
token() { awk '/^published / {t = $NF} END {print t}' "$1"; }
LP=$(token $B/logs/fit_prefill-steps.log) LD=$(token $B/logs/fit_decode-steps.log)
HP=$(token $B/logs/fit_prefill-host.log) HD=$(token $B/logs/fit_decode-host.log)
# the simulated deployment: the router's wall-clock detectors off, as deploy.sh requires
ATOMESH=$ATOMESH $T/scripts/compass/deploy.sh $B/step_linear run --kv-over-network --network nic-400g \
  --step-linear $LP --step-linear $LD --host-laws $HP --host-laws $HD $P $S \
  --prefill -- $(args P) --decode -- $(args D) \
  --router -- ${ROUTER% --request-timeout-secs 1800} --disable-health-check --disable-retries \
  > $B/logs/sim.log 2>&1 &
until [ -s $B/step_linear/server.json ]; do sleep 10; done
HARNESS_PYTHON=$SIM_PY $T/scripts/compass/client.sh $B/step_linear --agentx --concurrency 128 --duration 1800 --stop
wait
PYTHONPATH=$T python3 $T/scripts/compass/one_real.py $B/real1 $B/step_linear
```

The recipe's router also takes `--dp-aware` (it picks each side's DP rank). Give it to
both runs or neither: simulated, `--dp-aware` makes the router an LP, which needs the
tree's clean atomesh and host laws stating `router_s` above the IPC hop, else
`deploy.sh run` refuses (`0 < router_in_s < router_s`); the `--stated-hop` above gives
it. Without it ATOM's own DP dispatch, `least_requests`, picks the rank on both runs.

The prefill side decodes nothing of its own: a request leaves at its first token, so
every decode step it runs is a dummy all four ranks run while sends finish (1985 a
rank in the CPU smoke's 400 s). Its law, fitted on no dummy, holds no decode vector;
the simulated run prices those steps 0 s under the treatment `idle DP group dummy`
(`05aaed2b3`) rather than refusing them. Real ones replay a decode graph at one
padding row, a few ms each, so this understates the prefill side's busy time: read
the treatment's count in the run's summary against the record's dummy steps.

## Where the error comes from (task 3)

- Per step: `PYTHONPATH=$T python3 -m atom.compass.validate.cost` on the real record
  (`README.md`, Cost accuracy) prices the record's own steps by the law: the step law's
  error with the schedule held fixed.
- Per schedule: `atom.compass.parity.compare` on the real and simulated `steps/`, the
  first step where they part per DP rank, and `routes.jsonl` for each request's rank
  (f1ed2adfc).
- Per request: each run's `request_split.json` (`report.split`), TTFT split into
  queue, prefill forwards, transfer and first decode; under `--kv-over-network`
  compare the transfer share against the real run's to check the link file.
- A rung or prefill bucket the law extrapolates shows in the simulated run's
  summary (`extrapolated`); a second real run at another concurrency fills it.
  At low concurrency that count also holds the idle ranks' dummy forwards, so read
  each vector's error from `validate.cost` on the real record instead.
- A law fitted at one concurrency also extrapolates across group composition: how
  many DP ranks a step runs busy beside dummy forwards. `real_pw_c128` holds nearly
  every step at four busy ranks and c=1 runs one. A rung of one record picks its MoE
  column holding out compositions, and that took c=1 decode from +34% to +18%
  (#3747). Its context slope and the prefill split between `tokens` and `moe_rows`
  still need a record at another composition. To predict concurrency C, fit on records
  on both sides of C, e.g. `real_pw_c1` and `real_pw_c128`. Each record is a
  positional argument with its own `--client-run`, as `run/conc_sims_pw.sh` passes
  one; the host laws then also fit `admit` (#3745).
- c=8 has the same two errors as c=1. Under the c=128 law its decode is +15% on
  totals, growing with context to +44% above 400k, and its prefill +22% at one
  busy rank. The pool `real_pw_c1` + `real_pw_c128` never saw c=8 and prices it
  +0.3% and +1.3%; its simulated run reads TPOT p50 +0.6% where the c=128 law's
  read +13.4%. A prefill hull past six features is pairwise (D58), so such a pool
  fits in 8 min into a 15 MB law that runs as fast as a one-record law. Pool the
  step law, not the host laws: c=128 under host laws pooled with c=1 reads TPOT
  p90 +9.8%, under its own -1.3%. Copy `host_laws` from the c=128 record's store
  into the pooled store (c=32: TPOT p50 -0.6%, E2E +0.2%). At c=8 the pooled host
  laws did better (TPOT p50 +0.6% against +2.0%), so the host laws' dependence on
  concurrency is still open (#3747). Rungs 48
  and 64 are reached by no record below c=256, and the law refuses them (D58,
  #3737), so a c=256 run on a pool of lower records is no prediction.
- E2E p50 moves with the requests a run finished and with each one's place in the
  schedule: c=8's real E2E p50 has a 95% interval of -8%..+9% on its own. Read
  one_real's paired E2E line under the table before calling an E2E error a bias.
- At c=1 the engine idles before each request, and its first forward enters about
  4 ms after it takes the request, about 1 ms more than a busy engine's. No host
  term charges that (#3746); in-sample TTFT p50 reads -6.1%. A simulated run's
  `request_queue_time` and `queue_s` end before the first forward's `E` and
  admission are charged, a real one's after, so compare their sum with
  `prefill_s`, or TTFT, not the queue alone.
- Until #3748 `compass fit host` fitted no `http_intake` past c=1 (two intakes
  that overlap hid every later lone request), and runs charged each request's
  intake 0 s: 3.7 ms at p50 of c=32's real front. With it fitted, the template
  render folded in, the queue's low end moves toward the real one in every run.
  c=32's TTFT p50 still swings: seven runs on `real_pw_c32` read -11.3% to -1.4%,
  the median falling where the TTFT density is thin, between the PrefillDelayer's
  stall fires and its long holds. The steadiest term those runs miss is the
  hand-over, the forward after a rank's prefill that waits in lockstep for the
  other ranks' prefill (p25 15-64 ms against 71).

## CPU smoke without a GPU

To check a change to the simulated path without a GPU: in a container with no device
nodes (`on_arch` declares gfx950 there), publish placeholder `memory_readings` marked
`assumed` at each configuration's key (`run.memory.key_fields` of the config
`drive.run._config` resolves), price with `--step-stub`, and drive with
`python -m atom.compass.parity.traffic PORT MODEL DIR` under `ATOM_COMPASS_RUN` (the
run file), `DIR/arrivals.json` holding synthetic `sent_ns`. None of its numbers mean
anything; it checks that the path runs. Both cells passed it at `4d725a45e`: 64
requests each, cell B on the intra-node link and under `--kv-over-network nic-400g`.

Cell B also ran its real client on CPU (aiperf from agentx-harness `56a0cf70` with this
tree's compass-harness, the recipe's cc-traces revision, sha256 `29b6a19e...`, c=128,
`--kv-over-network nic-400g`): `--traces 0-255 --duration 300` behind a plain router
and behind the recipe's `--dp-aware` one (a host entry stating `router_s`), and
`--agentx --duration 600` behind `--dp-aware`: 3765 profiling and 1422 warmup
requests, 200612 steps priced, no refusal. Its KV transfers took 7 ms at p50 and
21 ms at p90 on that link (636 and 1780 blocks); `request_split.json`'s
`kv_transfer_s`, from prefill's return to decode's first forward, read 0.43 s at
p50, most of it the prefill side's next forward, which hands the first token over
(ATOM's deferred output): with prefill saturated that forward is a long chunk, a
TTFT term the law prices as prefill time, not as transfer.
