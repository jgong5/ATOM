**Bug in landed code (#170, #428).** On the producer (prefill) side, `scheduler.py:2767-2774` calls `request_finished` and then parks every finished sequence in `deferred_free_blocks`; only a `finished_sending` report frees it (`scheduler.py:3038-3046`). The simulated connector reports `finished_sending` only for requests announced in `reqs_to_save` (`atom/compass/kv/connector.py:149-151`, `:171-174`), and its scheduler half never announces one: `build_connector_meta` (`connector.py:302-320`) adds only `reqs_to_recv`, and `request_finished` (`connector.py:322-331`) only attaches the relay blob. The only place `add_new_req_to_save` appears under `atom/compass` or `tests/compass` is a test that hands metadata to the worker directly (`tests/compass/test_kv_simulated_connector.py:99`). So every prefill's blocks stay held for the rest of the run, and a simulated prefill deployment runs its KV pool dry. Found by the doc 01 §D6-§D8 PR (#448).

**What to do.** Make the producer free a finished request's blocks at a priced time. If the Mooncake-hook rework (#466) is claimed first, it fixes this (it frees at `max(a, r) + T` from `process_completions`) and this issue closes with it. Only if this is taken alone: the smallest fix is the scheduler half announcing each finished producer request in `reqs_to_save`, idempotently (`request_finished` runs twice per request, `scheduler.py:2708` and `:2768`), which the worker half already prices and releases. Add a CPU test that goes through the real `Scheduler`, not the worker directly.
