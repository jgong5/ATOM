## What this adds

`atom/compass/ir/applicability.py` — `GuardedApplicability`, a subclass of the
marker ABC `Applicability` that #60 left empty, plus `Verdict`. A graph's
validity statement is in two parts, and the module's whole job is to decide one
step against them and to be unable to change the record while doing it.

`decide(key=…, sizes=…)` returns a `Verdict`: admitted, or refused with a reason
that names the condition and what the step offered. It is never an exception,
because a refusal is a result.

## The discrete key — what ATOM already states, and what it does not

`atom/model_engine/run_labels.py` is the existing emitter, and the key's field
taxonomy is taken from it rather than invented. What `build_run_label` already
carries:

| Key field | Where it comes from in the label |
|---|---|
| forward mode | the prefix: `prefill` / `decode` / `eager_decode` |
| replayed vs eager | the same prefix — `decode` is the CUDA-graph path, `eager_decode` is not, and `prefill` is always eager |
| `is_dummy_run` | the `dummy_` prefix (`dummy_decode`, `dummy_eager_decode`, `dummy_prefill`) |
| `tbo_on` | ` tbo=1`, appended from `forward_context.ubatch_slices is not None` |
| padded batch width | `bs=117/128`, but only when the replayed width differs from the scheduled one |

Four things it does **not** state, each of which a key built only from the label
would be silently blind to:

1. **`has_cached`.** It is not a label field. The eager label carries `ctx=` per
   sequence and truncates to the first three past five sequences
   (`[a, b, c]...+N`); the replayed decode label carries no `ctx` at all, only
   `p=`/`d=` counts. `AttentionMetadata.has_cached` is what the attention
   backends actually branch on (`atom/model_ops/attentions/backends.py` sets it,
   and `attention_mha.py`, `triton_mla.py` and `aiter_attention.py` all take
   different paths on it).
2. **`produces_output()`.** `ScheduledBatch.produces_output()` is what the head
   and `postprocess` are skipped on (`model_runner.py`, `pp_engine_core.py`);
   no label field reports it. A pure middle-chunk prefill produces nothing and
   costs differently from a final chunk of the same width.
3. **The attention backend.** Not emitted anywhere in the label.
4. **The speculation width, except on one path.** `spec=` is appended only on
   the CUDA-graph branch and only when `num_spec_step > 0`, so a width of zero
   and "this step is not speculating" are the same absence, and an eager or
   prefill step that is speculating says nothing at all.

A fifth, structural point: the label is a **string built for a profiler**, lossy
and truncated, and `tools/parse_trace.py` reads it back with a regex. The key
here is the values, not their rendering. What the module fixes is not which
fields exist — that stays the recording side's statement — but that the two
sides must carry the **same** field names: a field one side omits is a condition
nobody checked, so it is refused and named rather than skipped.

## The symbolic domain, and the guard count that proves nothing moved

`GuardedApplicability.from_shape_env(shape_env, key)` reads `shape_env.guards`
(each guard's `.expr`) and `shape_env.var_to_range` (as `name -> (lower, upper)`).
Both are attribute reads. Evaluation substitutes the step's sizes into the
recorded expression with `subs`, which is a rewrite and records nothing; the
result must have no free symbols left before its truth is taken.

Both halves of the domain are kept, because they answer different questions: a
guard is a branch that was **taken**, a range also carries the bound that no
branch asked about — a size recorded as at least 2 describes a graph that says
nothing about a batch of 1. Guards are evaluated first, so a refusal names the
branch where there is one.

Measured on node 18 in `xiaobizh_n18_cpu` at `f4a4fc3ad`, one tracing run per
path, branching on `tokens > 128`:

deciding installs none.

## Refusals

Five kinds, all naming both sides:

* a guard that is false — `guard `s93 > 128` is false at s93=17`
* a guard over a symbol the step does not bind — `guard `s93 <= 128` is over ['s93'], which the step does not bind; it binds ['other']`
* a size outside a recorded range — `the record holds s93 in [2, 128]; the step binds s93=1`
* a key field that differs — `mode was recorded as 'decode' and the step states 'prefill'`
* a key field one side does not state — `the step states nothing about ['tbo']` / `the record states nothing about ['pipeline_stage']`

A key with no conditions in it is refused at construction: it would admit every
forward mode, every backend and the dummy runs, which is the claim the key
exists to stop being made by default.

## Dev record — what was decided that the brief did not cover

1. **Guards are checked before ranges.** With ranges first, a prefill record
   refused a decode step by naming `the record holds s93 in [129, int_oo]`,
   which is true but is not the branch. The guard is the statement the tracing
   run actually made, so it is the one a refusal should lead with; the ranges
   then catch what no branch asked about. This was a test failure before it was
   a decision.
2. **Every symbol the domain names must be bound, or the step is refused.**
   `var_to_range` can hold a symbol no guard mentions. Refusing is the stricter
   reading, and it is the one that matches "detected rather than mispriced" — a
   graph whose domain mentions a size the step cannot state has not been shown
   to describe it. If a capture path later finds this too strict, the narrowing
   belongs on the recording side (pass the ranges it can decide), not here.
3. **Key field sets must match exactly, in both directions.** A recorded field
   the step omits, and a step field the record omits, are both refused by name.
   A missing field is a condition nobody checked, and silently ignoring it is
   the exact failure the key exists to prevent.
4. **The key's field names are the recording side's to choose.** The module
   fixes only that both sides state the same ones. The eight fields used
   throughout the tests are the ones the design names, spelled as the label
   spells them where the label has them.

## Blocking: `_as_key`'s `hash(value)` could install a guard — fixed

The reviewer is right, and the finding is better than the defect. `hash()` on a
key's value is itself an operation on the value, and the two symbolic types
answer it in **opposite** directions:

| | `__hash__` |
|---|---|
| `torch.SymInt` | **raises** `TypeError: unhashable type: non-nested SymInt` — the sizes half was safe by accident |
| `torch.SymBool` | **answers**, by `hash(builtins.bool(self))` — its own comment reads `# Force specialization` |

So the gate meant to keep unsafe values out was itself the leak, on the key
half only, and silently. Re-measured here at `d1e828ba3`:

```
== 1. the SymBool hash, and the allowlist that replaces it
   SymBool built;   guards = 0 []
   key refused:     guards = 0 -> the value of 'has_cached' is a SymBool. A condition matched by equality is a b ...
   hash(SymBool) -> 1  guards = 1 ['s21 <= 4096']
```

**Fix: a positive type list, and nothing is asked anything.** `_CONDITION_TYPES`
is `(bool, int, str, enum.Enum, type(None))`. A value is one of those or it is
refused by name. That closes the reviewer's other two consequences of the same
line at the same point, both of which broke the contract that `decide` returns a
verdict rather than raising on a mismatch:

```
== 2. a tensor key, which used to raise from inside the comparison
   refused: the value of 'ctx' is a Tensor. A condition matched by equality is a bool, an int, a str, an en
```

* a `SymBool` against a Python bool used to raise `TypeError: BooleanAtom not allowed` from `==`;
* a multi-element `torch.Tensor` used to raise `RuntimeError: Boolean value of Tensor is ambiguous` — and `ctx` is exactly that kind of field.

I have taken the reviewer's framing that reachability on today's ATOM code is
**not** established — both booleans are Python bools today — and have not
claimed otherwise anywhere in the code or here. The fix stands on the other
argument: a defence that depends on a caller never passing the wrong type is
not a defence.

The module docstring's claim that "the wrong idiom cannot happen inside the
module" was **false for keys** and is withdrawn. It now says which half is
defended how, and why the two halves need different defences.

## Decision 2b: what `decide` does with a symbol that has a range and no guard

The reviewer's measurement is reproduced — an unbacked `u0` lands in
`var_to_range` as `VR[-int_oo, int_oo]` with no guard, and the old rule then
refused every step, naming a symbol no step could bind. On the MoE model this is
designed for, that is total refusal.

**Decided, at record time as asked: `from_shape_env` records a range only for a
symbol some guard branched on.** Reasons, in the order they matter:

1. A symbol no guard mentions is one whose value never changed which path was
   taken. The record is a straight-line trace; its validity does not depend on a
   size nothing branched on. So a range over one is not a condition the record
   earned — it is the tracing run's own bookkeeping.
2. For a data-dependent size it is not merely unnecessary, it is
   **unanswerable**. Branching on an unbacked symbol raises
   (`GuardOnDataDependentSymNode`) rather than installing a guard, which is
   exactly why it arrives with no guard and no bound; and a step cannot bind a
   count the router had not produced when the trace ran.
3. The range of a symbol a guard **does** name is kept, and still earns its
   place — the reviewer confirmed this and it is unchanged. A decode record
   holds its token count in `[2, 128]`; the guard says only `<= 128`, so the
   lower bound is carried by the range alone and nothing else refuses a batch of
   one.

I chose this over a test for an unbounded interval. `int_oo.is_finite` is
**`True`** on torch 2.10 — measured — so the obvious "drop the ranges that bound
nothing" test does not work, and a rendering comparison against `int_oo` would
be reading a spelling. "Did a guard branch on this symbol?" is a question the
record can answer about itself.

Dropping a range at record time is not the same as ignoring one: where a range
is in the record, the step still has to answer it. There is a test for each half.

```
== 3. a data-dependent size no branch touched
   var_to_range    {'s93': 'VR[2, 128]', 'u0': 'VR[-int_oo, int_oo]'}
   guards          ['s93 <= 128']
   recorded ranges {'s93': ('2', '128')}
   step s93=17 -> True
   step s93=1  -> the record holds s93 in [2, 128]; the step binds s93=1
   guards after    1
```
